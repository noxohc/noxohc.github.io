## 1. 사고 개요

2026년 3월 31일, JavaScript에서 널리 사용되는 라이브러리인 Axios에서 소프트웨어 공급망 공격이 발생했다.

공격자는 Axios 관리자의 계정을 탈취하고 악성코드가 포함된 버전을 공식 패키지 저장소에 배포했다. 이로 인해 정상적인 라이브러리를 설치하려던 개발자들의 컴퓨터까지 악성코드에 감염될 위험에 놓였다.

- 발생일: 2026년 3월 31일
- 공격 유형: 소프트웨어 공급망 공격
- 영향받은 버전: Axios 1.14.1, 0.30.4
- 영향받는 운영체제: Windows, macOS, Linux

## 2. 배경지식

### 2.1. Axios와 npm

Axios는 JavaScript에서 서버에 데이터를 요청하거나 전달할 때 사용하는 라이브러리이다. 개발자가 통신 기능을 처음부터 구현하지 않아도 쉽게 사용할 수 있도록 도와준다.

npm은 이러한 JavaScript 라이브러리를 설치하고 관리할 수 있는 패키지 관리 도구이자 패키지 생태계이다.

개발자는 다음과 같은 명령어를 통해 Axios를 설치할 수 있다.

```bash
npm install axios
```

### 2.2. 의존성(Dependency)

하나의 프로그램이 동작하기 위해 다른 라이브러리나 프로그램을 필요로 하는 관계를 의존성이라고 한다.

npm을 통해 패키지를 설치하면 해당 패키지가 필요로 하는 다른 패키지도 함께 설치된다. 따라서 의존성에 악성코드가 포함되어 있다면 정상적인 패키지를 설치하는 과정에서도 문제가 발생할 수 있다.

### 2.3. 소프트웨어 공급망 공격

소프트웨어 공급망 공격은 공격 대상의 시스템을 직접 해킹하는 대신, 대상이 신뢰하고 사용하는 소프트웨어나 개발 도구를 침해하는 공격이다.

하나의 라이브러리를 침해하는 것만으로도 해당 라이브러리를 사용하는 여러 개발자와 기업에 영향을 줄 수 있다는 특징이 있다.

## 3. 공격 과정

### 3.1. 관리자 계정 탈취

공격자는 Axios 유지관리자의 계정을 침해하여 공식 패키지를 배포할 수 있는 권한을 확보했다.

유지관리자는 라이브러리를 관리하고 새로운 버전을 배포하는 사람이다. 따라서 해당 계정이 탈취되면 공격자도 정상적인 관리자인 것처럼 패키지를 배포할 수 있다.

### 3.2. 악성 패키지 배포

공격자는 Axios 1.14.1과 0.30.4 버전에 `plain-crypto-js`라는 악성 패키지를 의존성으로 추가했다.

개발자가 감염된 Axios 버전을 설치하면 npm의 의존성 관리 기능에 의해 악성 패키지도 함께 설치되었다.

### 3.3. 악성코드 실행

악성 패키지에는 설치 과정에서 자동으로 실행되는 `postinstall` 스크립트가 포함되어 있었다.

이를 통해 원격 접근 트로이목마(RAT)가 설치될 수 있었다.

RAT는 공격자가 감염된 컴퓨터에 원격으로 접근하고 제어할 수 있도록 하는 악성코드이다. 이를 통해 추가적인 정보 탈취나 시스템 침해가 발생할 수 있다.

## 4. 근본적인 원인

이번 사고의 직접적인 원인은 유지관리자 계정의 탈취이다. 그러나 피해가 여러 개발자에게 확대될 수 있었던 데에는 다음과 같은 문제가 존재했다.

- 개인 계정에 중요한 패키지 배포 권한이 집중되어 있었다.
- 비정상적인 패키지 배포를 사전에 차단하는 보호 장치가 충분하지 않았다.
- 패키지에 추가된 악성 의존성을 배포 전에 발견하지 못했다.

결과적으로 정상적인 패키지 배포 과정 자체가 공격 수단으로 이용되었다.

## 5. 사고 대응

악성 버전은 발견 이후 npm 저장소에서 제거되었다. 또한 유지관리자는 침해된 환경과 인증 정보를 정리하고, 사용자들에게 감염 여부를 확인하도록 안내했다.

영향을 받은 사용자는 다음과 같은 조치를 취할 필요가 있다.

- 악성 버전 삭제 및 검증된 정상 버전 사용
- 악성코드 감염 여부 확인
- 노출 가능성이 있는 비밀번호, API 키, 인증 토큰 교체
- 의존성 및 설치 기록 확인

이미 악성코드가 실행되었다면 Axios를 삭제하는 것만으로는 문제가 해결되지 않을 수 있으므로 시스템 전체에 대한 점검이 필요하다.

## 6. 미흡했던 부분 및 개선 방안

이번 사건에서는 계정이 탈취된 이후 공격자가 공식 패키지를 배포하는 과정에서 추가적인 검증이 충분하지 않았다는 점이 문제였다.

이를 개선하기 위해서는 다음과 같은 보안 조치가 필요하다고 생각한다.

- 배포 권한 최소화 및 중요 작업에 대한 추가 승인
- 신뢰할 수 있는 자동화 환경에서만 패키지를 배포하도록 설정
- 새로운 의존성과 설치 스크립트에 대한 자동 검사
- 비정상적인 패키지 배포를 탐지하는 모니터링 시스템 구축

사용자 역시 라이브러리를 설치할 때 검증된 버전을 사용하고 의존성에 어떤 변화가 발생했는지 확인하는 습관이 필요하다.

## 7. 느낀 점

이번 사건을 통해 공식 저장소에서 제공하는 라이브러리라고 해서 항상 안전한 것은 아니라는 점을 알게 되었다.

특히 공격자가 직접 여러 시스템을 공격하지 않고도 하나의 라이브러리를 통해 많은 사용자에게 영향을 줄 수 있다는 점이 인상적이었다.

소프트웨어를 개발할 때는 직접 작성한 코드뿐만 아니라 외부 라이브러리와 배포 과정의 보안까지 고려해야 한다고 생각한다.
