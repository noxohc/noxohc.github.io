## 1. 사고 개요

2026년 8월 27일, 클라우드 서비스 배포 플랫폼인 Zeabur에서 보안 사고가 발생했다.

공격자는 사용자가 배포한 웹 서비스의 취약점을 이용해 내부 시스템에 침입했다. 이후 관리자 권한을 획득하고 운영 데이터베이스까지 접근하면서 사용자 계정 정보와 API 키, 데이터베이스 비밀번호 등의 민감한 정보가 노출되었다.

- 발생일: 2026년 8월 27일
- 공격 유형: 원격 코드 실행, 권한 상승, 내부망 침투
- 관련 취약점: CVE-2026-7644
- 주요 피해: 사용자 계정 정보 및 프로젝트 환경 변수 노출

## 2. 배경지식

### 2.1. 클라우드 서비스와 Zeabur

클라우드 서비스는 사용자가 직접 서버를 구매하고 관리하지 않아도 인터넷을 통해 서버, 저장 공간, 데이터베이스 등을 이용할 수 있도록 제공하는 서비스이다.

Zeabur는 개발자가 만든 웹사이트나 프로그램을 이러한 클라우드 환경에 쉽게 배포할 수 있도록 지원하는 플랫폼이다.

### 2.2. 컨테이너와 클러스터

컨테이너(Container)는 프로그램과 프로그램 실행에 필요한 환경을 하나로 묶어 독립적으로 실행할 수 있도록 하는 기술이다.

클러스터(Cluster)는 여러 컴퓨터나 서버를 하나의 시스템처럼 관리하는 구조이다.

여러 사용자가 하나의 클러스터를 공유하는 경우, 각 사용자의 서비스가 서로의 시스템에 함부로 접근하지 못하도록 접근을 제한하는 것이 중요하다.

### 2.3. API 키와 환경 변수

API 키는 프로그램이 특정 서비스에 접근할 권한이 있음을 확인하는 데 사용되는 인증 정보이다.

환경 변수(Environment Variable)는 프로그램이 실행될 때 필요한 설정 정보를 저장하는 방법이다. API 키나 데이터베이스 비밀번호 등을 소스코드에 직접 작성하지 않고 환경 변수에 저장하기도 한다.

이러한 정보가 노출되면 공격자가 정상적인 사용자나 관리자인 것처럼 서비스에 접근할 수 있다.

### 2.4. 원격 코드 실행(RCE)

원격 코드 실행은 공격자가 외부에서 대상 시스템에 원하는 코드를 실행할 수 있는 취약점이다.

공격자가 시스템을 직접 조작할 수 있게 된다는 점에서 위험성이 높으며, 추가적인 정보 탈취나 권한 상승으로 이어질 수 있다.

## 3. 공격 과정

### 3.1. 웹 서비스 취약점 악용

공격자는 Zeabur의 공유 클러스터에서 실행 중인 NextChat이라는 AI 채팅 서비스의 취약점을 이용했다.

해당 취약점은 외부 도구와 연결하는 MCP 기능의 권한 검증이 충분하지 않아 발생했으며, 공격자는 이를 통해 컨테이너 내부에서 코드를 실행할 수 있었다.

### 3.2. 내부 네트워크 접근

공격자는 침입한 컨테이너에서 다른 내부 시스템으로 접근했다.

당시 공유 클러스터는 프로젝트 간 네트워크 접근을 충분히 제한하지 못하고 있었다.

이로 인해 공격자는 내부 서비스 연결 정보를 저장하는 캐시에 접근하여 기존 방식으로 발급된 API 키를 확보할 수 있었다.

### 3.3. 관리자 권한 획득

공격자가 확보한 API 키 중에는 관리자 권한을 가진 키가 포함되어 있었다.

이를 통해 내부 관리 서비스의 설정 정보에 접근했고, 그 과정에서 AWS의 최고 관리자(root) 인증 키까지 확보했다.

AWS root 계정은 클라우드 계정의 거의 모든 기능을 제어할 수 있는 높은 권한을 가진 계정이다.

### 3.4. 운영 데이터베이스 접근

공격자는 획득한 권한과 기존 내부 연결 경로를 이용해 운영 데이터베이스에 접근했다.

결과적으로 사용자 계정 정보와 프로젝트 환경 변수에 저장된 민감한 인증 정보를 읽을 수 있었다.

전체적으로 하나의 웹 서비스에서 시작된 침해가 내부 네트워크, 관리자 계정, 클라우드 인프라, 운영 데이터베이스로 확대된 것이다.

## 4. 근본적인 원인

직접적인 침입 원인은 NextChat의 원격 코드 실행 취약점이었지만, 피해가 확대된 데에는 여러 구조적인 문제가 존재했다.

### 4.1. 네트워크 격리 부족

개별 컨테이너가 침해되더라도 다른 내부 시스템에는 접근할 수 없어야 한다.

그러나 당시 Zeabur에서는 이러한 접근 제한이 충분하지 않았다.

### 4.2. 과도한 권한 부여

기존 API 키는 사용 가능한 기능과 접근 범위를 세부적으로 제한하기 어려웠으며 만료 기간도 지원하지 않았다.

필요 이상의 권한을 가진 인증 정보가 노출되면서 공격 범위가 확대되었다.

### 4.3. 인증 정보 관리 미흡

내부 캐시와 환경 변수에 중요한 관리자 인증 정보가 저장되어 있었다.

이로 인해 하나의 인증 정보를 탈취한 공격자가 더 높은 권한을 연속적으로 획득할 수 있었다.

## 5. 사고 대응

Zeabur는 사고 이후 다음과 같은 조치를 실시했다.

- 기존 Legacy API Key 인증 방식 비활성화
- 내부 인증 정보 교체
- 공유 클러스터와 중요 시스템 사이의 접근 통제 강화
- API 키의 권한 범위와 만료 기간 설정
- 비정상적인 권한 변경 및 데이터베이스 접근 탐지 강화
- 영향을 받은 사용자에게 외부 서비스 인증 정보 교체 안내

그러나 2026년 10월 14일, Zeabur에서 추가적인 보안 사고가 발생했다.

이후 Zeabur는 두 차례의 보안 사고와 운영상의 어려움 등을 고려하여 2026년 12월 31일까지 서비스를 종료할 계획이라고 발표했다.

## 6. 미흡했던 부분 및 개선 방안

이번 사고에서 가장 큰 문제는 개별 서비스의 침해가 플랫폼 전체의 보안 문제로 확대되었다는 점이다.

이를 방지하기 위해 다음과 같은 개선이 필요하다고 생각한다.

- **네트워크 분리:** 사용자 서비스와 관리자 시스템 사이의 접근을 제한한다.
- **최소 권한 원칙:** 각 서비스에 실제로 필요한 권한만 부여한다.
- **인증 정보 관리:** 최고 관리자 인증 키의 사용을 최소화하고 단기 인증 정보를 활용한다.
- **모니터링 강화:** 평소와 다른 관리자 접근이나 대량 데이터 조회가 발생하면 즉시 탐지한다.
- **지속적인 보안 점검:** 오래된 시스템이나 폐기 예정인 기능도 실제 운영이 종료될 때까지 관리한다.

특히 사고 이후 추가적인 보안 사고가 발생했다는 점에서, 단순히 확인된 취약점을 수정하는 것뿐만 아니라 전체 시스템에 대한 보안 점검이 필요하다고 생각한다.

## 7. 느낀 점

이번 사건을 통해 하나의 취약점이 반드시 하나의 시스템에만 영향을 주는 것은 아니라는 점을 알게 되었다.

개별 웹 서비스에서 시작된 공격이 관리자 권한과 운영 데이터베이스 침해로 이어진 과정이 인상적이었다.

모든 취약점을 완벽하게 제거하기는 어렵기 때문에, 일부 시스템이 침해되더라도 다른 시스템까지 피해가 확대되지 않도록 설계하는 것이 중요하다고 생각한다.
